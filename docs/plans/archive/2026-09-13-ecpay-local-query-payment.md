# ECPay 本地金流串接：以主動查詢驗證付款

- 建立日期：2026-09-13
- 狀態：已確認方案，待實作與驗證
- 依據：本次對話確認的 ECPay 串接計畫與使用者選項
- Skill：[ECPay](../../.agents/skills/ecpay/SKILL.md)
- 本文件記錄本機主動查詢付款功能的實作範圍與驗證結果。

## User Story

作為花漾生活的購買者，我希望能從本地網站前往綠界測試付款頁完成信用卡付款，並在返回訂單頁後查看由後端驗證的付款結果。

作為本地開發者，我的伺服器無法接收綠界 Server Notify，因此需要由本地 Node.js 後端主動呼叫綠界查詢 API，驗證回應後更新訂單。關閉瀏覽器不應中止背景查詢；重新啟動伺服器後應恢復待查交易。

作為付款失敗的購買者，我希望在綠界明確確認前次交易失敗後，可以針對同一訂單再次付款；付款結果未知時不能產生另一筆交易，以避免重複付款。

## Spec

### 1. 已確認範圍

- 使用 ECPay AIO **測試環境信用卡一次付清**，由瀏覽器跳轉綠界付款頁；本機主動查詢不涵蓋需要 Server Notify 的離線付款方式。
- 本地後端負責簽章、主動查詢與更新訂單，不依賴 Server Notify。
- 採背景排程及手動查詢，程式重新啟動後恢復待查交易。
- 付款金額固定取已保存的 `orders.total_amount`，同步移除前台加收運費及滿額免運的矛盾顯示。
- 綠界明確確認失敗後，允許同訂單重新付款；未確認結果時不建立第二筆交易。
- 不包含正式收款、ATM／超商、退款、發票或物流。
- 沿用 CommonJS、現有會員認證及 `{ data, error, message }` 回應格式。

### 2. 本地模式驗證關卡

AIO 的 `ReturnURL` 仍為必填。測試設定使用獨立、無業務處理的本機占位網址 `http://localhost/ecpay/notify-unavailable`，與 `ClientBackURL` 分離；付款狀態不依賴此網址，而由本機後端主動查詢並驗證。

參考：[官方建單規格](https://developers.ecpay.com.tw/2862/)。實作前重新核對 skill references 指向的即時規格。

### 3. 付款流程與 API

1. 會員建立訂單，維持既有建單扣庫存、保存商品快照及清購物車流程。
2. 訂單詳情改為「前往綠界付款」，移除直接設定成功／失敗的按鈕及舊 `PATCH /api/orders/:id/pay`。
3. 新增 `POST /api/orders/:id/payment`，要求本人 JWT，不接受客戶端金額或付款結果。後端保存付款紀錄後，在 envelope 的 data 中回傳 `{ action, fields }`；前端使用 DOM 建立表單，在同一分頁 POST 至綠界，不使用 iframe。
4. 使用 `ClientBackURL` 返回本機訂單詳情，不設定 `OrderResultURL`。返回連結及任何 `payment` query 都不能改變付款狀態。
5. 新增 `POST /api/orders/:id/payment/verify`，要求本人 JWT，由後端執行到期查詢；未到期回傳目前狀態與下次可查時間，不繞過節流。
6. 訂單詳情回應新增 `payment` 摘要，包含目前交易、查詢結果、最後／下次查詢時間及可否重試。不回傳密鑰或完整原始查詢資料。

付款表單使用 `ChoosePayment=Credit`；`CheckMacValue` 是提交綠界所需欄位。HashKey／HashIV 只能留在後端，不得出現在前端或日誌。查詢回應的原始簽章不需要提供給瀏覽器。

### 4. 資料與相容性

- 新增 `payment_attempts` 表，以外鍵連結訂單，保存唯一 `MerchantTradeNo`、環境／商店識別、金額快照、付款表單必要資料、交易狀態、綠界交易編號、付款時間與查詢排程欄位。
- 交易編號使用不超過 20 字元的隨機英數字，另設 UNIQUE；不直接使用含連字號的現有 `order_no`。
- 每筆訂單最多一個未確認付款紀錄，以資料庫約束及交易確保並發點擊不會建立多筆。
- 使用可重複執行的新增表／索引初始化，不重建既有表、不刪除舊資料。
- 既有 paid／failed 訂單保留原狀；只有具備已驗證失敗付款紀錄的訂單才開放重試，不能把舊模擬失敗紀錄當成綠界確認。
- 付款重試不再次扣庫存；成功查詢不再次扣庫存，失敗不回補庫存。
- 保存查詢排程與必要的鎖定／暫停資訊，確保重新啟動不會遺失待查交易或繞過限制。

### 5. ECPay 通訊與驗證

- 封裝 CommonJS 金流服務，使用 Node 內建 `crypto`、`fetch`，依 skill 實作 SHA256 CheckMacValue、特殊字元編碼與 timing-safe 比對。
- 簽章只在後端計算；交易時間使用台北時區。付款表單只帶必要參數，金額來自 DB，商品文字先清理並限制長度，再計算簽章。
- 查詢使用 `QueryTradeInfo/V5`，送出 URL-encoded POST，設定 30 秒逾時。TimeStamp 使用 Unix 秒數。
- 解析回應後驗證 CheckMacValue、MerchantID、MerchantTradeNo、TradeAmt，全部符合才允許更新付款狀態。
- 查詢網路操作不放進同步 SQLite transaction；收到並驗證回應後，才以 transaction 更新付款紀錄與訂單。
- 已確認 paid 不被較舊查詢降級。

| 已驗證的查詢結果 | 付款與訂單處理 |
| --- | --- |
| `TradeStatus=1` | 記錄已付款，訂單改為 paid |
| `TradeStatus=0` | 保留 pending，依排程繼續確認 |
| `TradeStatus=10200095` | 記錄明確失敗，訂單改為 failed，允許同訂單以新交易編號重試 |
| 逾時、查無交易、格式錯誤、驗簽失敗、金額不符或未知代碼 | 只記錄未確認與錯誤分類，不判付款失敗、不允許新交易 |

參考：[官方查詢規格](https://developers.ecpay.com.tw/2890/)、[檢查碼機制](https://developers.ecpay.com.tw/2902/)、[介接注意事項](https://developers.ecpay.com.tw/2858/)。

### 6. 排程與故障處理

- 排程僅由 `server.js` 啟動，匯入 app 的測試不啟動背景工作。
- 未偵測到付款流程返回時，付款表單產生後 10 分鐘開始查詢。若同一瀏覽器完成本次付款流程後經 `ClientBackURL` 返回，前端只記錄返回事件並要求後端立刻主動查詢一次；返回事件本身不能改變付款狀態，查詢仍須驗簽、比對商店／交易編號／金額，且仍受全域節流與 403 暫停約束。未確認交易每隔 10 分鐘再查。
- 每 30 秒檢查本機待辦；對外請求序列執行，至少間隔 5 秒。背景及手動查詢共用同一排程、鎖定及節流機制。
- 收到綠界 HTTP 403，持久保存全域暫停時間，停止對外查詢 30 分鐘；重新啟動亦不能繞過。
- 每筆自動追查最多 24 小時，之後保留未確認狀態並停止自動查詢；使用者可手動補查，仍遵守間隔。時間到期不自動判失敗。
- 記錄交易識別、查詢時間及錯誤分類，避免記錄密鑰、簽章、卡片或完整付款資料。

上述每 30 秒本機掃描與頁面讀取狀態，均不等於每 30 秒呼叫綠界。綠界對未收到通知的信用卡付款建議付款後 10 分鐘查詢，仍未付款則再隔 10 分鐘查詢；應避免高頻對外輪詢。

### 7. 畫面、設定與文件

- 訂單頁顯示「尚未付款／等待確認／已付款／付款失敗」及下次查詢時間。未建立交易時提供付款；等待確認時只提供查詢；僅綠界確認失敗後才提供重試，避免重複付款。
- 頁面可定期讀取本機訂單狀態，但不能因此頻繁呼叫綠界；離開頁面後背景排程繼續運作。
- 前台付款文案採消費者語言，例如「前往付款」、「付款狀態確認中」與「付款成功」；測試環境、供應商、後端驗簽與查詢排程等技術資訊只保留在程式、測試與文件。購物車、結帳、訂單與付款金額應一致。
- 沿用 `ECPAY_MERCHANT_ID`、`ECPAY_HASH_KEY`、`ECPAY_HASH_IV`、`BASE_URL`；`ECPAY_ENV` 僅允許 `staging`，其他值明確拒絕，避免誤接正式環境。
- 使用者現有 `.env`、`.codex` 設定不因文件或功能開發被覆寫；範本與文件不記錄正式密鑰。
- 同步更新 OpenAPI、AGENTS 與相關 docs，將模擬付款的舊描述改為實際完成的金流行為，清楚標示仍未驗證的限制。

### 8. 測試與完成標準

在獨立 SQLite 副本執行既有 32 個案例及新增金流測試，外部 API 以可注入 HTTP client 模擬；不能使用本機開發資料庫作測試 fixture。

| 驗證區域 | 必要案例 |
| --- | --- |
| 簽章 | skill 測試向量、中文、空格、特殊字元、錯誤及長度不符簽章 |
| 回應驗證 | 錯誤金額、商店、交易編號、格式錯誤、未知代碼不得入帳 |
| 狀態 | 成功、未付款、明確失敗、未知結果、paid 不降級 |
| 排程 | 首次與後續間隔、403 暫停、重啟恢復、24 小時停止自動追查、手動補查遵守節流 |
| 權限及並發 | 跨使用者拒絕、並發付款不重複建交易、背景與手動查詢不重複出站 |
| 重試與庫存 | 明確失敗後新交易編號、未知結果不得重試、庫存不重複扣減、不回補 |
| 升級及金額 | 初始化可重跑、舊訂單保留、前端與保存／送綠界金額一致 |
| 建置 | CSS 建置與 OpenAPI 產生及契約核對 |

### 實作與驗證紀錄

2026-09-13 已完成：新增 `payment_attempts`／排程狀態表、AIO 測試信用卡付款表單（`ChoosePayment=Credit`）、QueryTradeInfo/V5 查詢與簽章驗證、付款排程、本人付款／查詢 API，以及訂單頁表單導轉。付款流程經 ClientBackURL 返回時，會立刻觸發一次仍受驗簽與節流保障的後端查詢；其他未確認交易維持 10 分鐘節流。

`npm test` 通過 8 個測試檔、40 個案例。付款相關測試涵蓋 CheckMacValue／表單、重複付款防護、驗簽成功入帳、金額不符、HTTP 403 暫停與節流；測試啟動時使用唯一的暫存 SQLite 檔，不會寫入開發資料庫。`npm run css:build` 與 `npm run openapi` 均成功。

本計畫以本機主動查詢驗證為完成範圍；Server Notify、公開 ReturnURL 與真實測試卡端對端付款均依作業限制排除，未作為完成條件。
